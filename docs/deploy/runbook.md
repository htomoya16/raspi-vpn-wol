## 運用開始前チェック

1. Frontend/Backend のテスト通過を確認する。
2. nginx 設定反映と `/api/health` 応答を確認する。
3. DB バックアップの手動実行とファイル生成を確認する。
4. API トークン（admin/device）で画面操作を確認する。
5. 外部公開されていない（VPN/LAN 内のみ）ことを確認する。

## PCシャットダウン

- 目的: VPN/LAN内のWindows PCを、起動ボタンの近くから個別に停止する。
- 前提: Windows側でOpenSSHサーバーを有効化し、ラズパイに `ssh`, `ssh-keygen`, `ssh-keyscan` があること。DB更新は通常の配備工程で `alembic upgrade head` を適用する。

1. 管理者トークンでPC詳細の「SSH設定」を開き、Windowsのローカルユーザー名・ポート・有効設定を保存する。IPは登録済みPC情報を使う。
2. 「鍵を作成・表示」を押し、表示した公開鍵登録コマンドを対象ユーザーのWindows PowerShellで実行する。管理者ユーザーならPowerShellも管理者として起動する。同じ公開鍵の行は重複追加せず、既存の鍵は保持する。
3. PC側で画面のホスト鍵確認コマンドを実行する。「PCのホスト鍵を取得」後、PC側で確認したSHA256指紋を入力して照合・登録する。
4. 「接続テスト」を実行する。固定の `echo` で確認し、停止命令は送らない。成功すると確認状態が保存される。
5. オンラインのPCで停止ボタンを押し、対象PCを確認して実行する。停止操作は認証済み `admin/device` とも利用できる。

- 通常停止は `shutdown /s /t 0`。未保存の作業などで停止しない場合があり、接続テスト成功だけでは停止権限まで確認できない。
- ジョブ結果は指示送信と通信停止の観測を分けて表示する。通信停止だけで電源断は断定しない。
- IP変更後は接続テスト、ユーザー名/ポート変更後はホスト鍵の再照合と接続テストが必要。有効/無効の切り替えだけなら確認結果を保持する。
- 鍵は既定 `/var/lib/wol/ssh/<key_id>/` に自動生成する（ディレクトリ700、鍵600）。API実行ユーザーに書き込み権限が必要。変更時は `WOL_SSH_KEY_DIR` を指定し、[systemd設定例](../../deploy/systemd/wol-api-shutdown.conf.example)を参照する。
- DBバックアップに秘密鍵は含まれない。DBと鍵ディレクトリを別途保全し、復元時は鍵ID・所有者・権限を合わせる。再生成ボタンで既存鍵は上書きしない。片方の鍵ファイルだけ欠けている場合は復元する。PC削除後も鍵ファイルは自動削除しない。
- 既存の秘密鍵を取り込む画面は未実装。Windowsの公開鍵登録と実機での接続・停止確認は利用者が行う。

## 日常確認（定期）

```bash
sudo systemctl status nginx --no-pager
sudo systemctl status wol-db-backup.timer --no-pager
sudo journalctl -u wol-db-backup.service -n 50 --no-pager
```

- 異常の目安:
  - nginx が `active (running)` でない
  - バックアップ service が連続失敗
  - backup ファイル世代が増えない

## 障害時初動

1. まず現行 DB を退避する（上書き前に必須）。
2. 直近バックアップから `app.db` を復元する。
3. `alembic upgrade head` でスキーマ整合を取る。
4. API サービス再起動後に `/api/health` を確認する。
5. adminトークン喪失時は `docs/deploy/token-ops.md` の break-glass 手順で復旧する。

## 復旧後確認

- PC 一覧取得が成功する。
- `POST /api/pcs/status/refresh` が成功する。
- 操作ログに復旧後イベントが記録される。
- 次回バックアップが通常どおり実行される。

## 運用時の注意点

- 復元時は「復元前 DB」の退避を省略しない。
- トークン失効/削除運用を実施し、不要トークンを放置しない。
- 仕様変更（nginx/systemd/DB運用）は同時に `docs/deploy/*` を更新する。
